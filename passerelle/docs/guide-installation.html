super-nono.cc · passerelle

Installer la passerelle, pas à pas

Une seule connexion pour tous tes sites, un hub sur super-nono.cc pour les ouvrir et les gérer, et les demandes d'accès validées depuis Discord. Coche chaque étape au fur et à mesure : ta progression reste dans ce navigateur.

Téléphone ─▶ Cloudflare ─▶ tunnel ─▶ LXC passerelle
                                     ├ cloudflared
                                     ├ Authentik  (auth.super-nono.cc)
                                     └ hub        (super-nono.cc)
                                          │
                       Authentik laisse passer ▼ les personnes connectées
                 recettes.super-nono.cc ─▶ LXC du site (IP:port)
                 botpanel.super-nono.cc ─▶ LXC du site (IP:port)

Compte environ 1 h 30 en tout, dont une bonne partie à attendre Google ou les DNS. Garde un bloc-notes ouvert pour coller les valeurs à reporter dans le fichier .env.

Phase 1 · e-mails

Brevo : envoyer depuis super-nono.cc

≈ 15 min

Les e-mails d'invitation et de mot de passe oublié partent par ton compte Brevo actuel, depuis une adresse du nouveau domaine.

Ajouter le domaine dans Brevo

  1. Brevo → en haut à droite, ton nom → Expéditeurs, domaines et IP dédiées → onglet Domaines → Ajouter un domaine.
  2. Écris super-nono.cc. Brevo propose de s'authentifier automatiquement avec Cloudflare : accepte, c'est le plus simple.
  3. Sinon, Brevo affiche 3 ou 4 enregistrements (code Brevo en TXT, DKIM, DMARC). Ajoute-les un par un dans Cloudflare → super-nono.cc → DNS → Enregistrements, en laissant le nuage gris (DNS uniquement).
  4. Reviens dans Brevo et clique Vérifier. Le domaine doit passer en « Authentifié » (parfois quelques minutes).

S'il existe déjà un enregistrement _dmarc sur le domaine, garde-en un seul.

Créer l'expéditeur

Onglet Expéditeurs → Ajouter un expéditeur : nom Super Nono, adresse acces@super-nono.cc. Comme le domaine est authentifié, pas besoin de boîte de réception réelle.

Générer une clé SMTP dédiée

  1. Ton nom → SMTP et API → onglet SMTP → Générer une nouvelle clé SMTP, nom passerelle.
  2. Copie la clé tout de suite (elle ne sera plus affichée) et note aussi l'identifiant affiché sur la même page (il ressemble à xxxx@smtp-brevo.com).
SMTP_USERl'identifiant SMTP
SMTP_PASSWORDla clé que tu viens de créer
SMTP_FROMSuper Nono <acces@super-nono.cc> (déjà rempli)
Phase 2 · facultatif

Google : « Se connecter avec Google »

≈ 10 min

Tu peux sauter cette phase et la faire plus tard : la connexion par e-mail et mot de passe marche sans.

Créer le projet et l'écran de consentement

  1. Va sur console.cloud.google.com, menu du haut → Nouveau projet, nom Passerelle.
  2. Menu → Google Auth Platform (ou API et services → Écran de consentement OAuth) → Commencer : nom de l'application Super Nono, ton e-mail d'assistance, public Externe.
  3. Onglet Audience → Publier l'application (« En production »). Sans ça, seuls les testeurs que tu ajoutes pourraient se connecter. Les données demandées (e-mail, nom) ne nécessitent aucune validation de Google.

Créer l'identifiant client

  1. Onglet Clients → Créer un client → type Application Web, nom Authentik.
  2. Dans URI de redirection autorisés, ajoute exactement :
https://auth.super-nono.cc/source/oauth/callback/google/
GOOGLE_CLIENT_IDl'ID client (finit par .apps.googleusercontent.com)
GOOGLE_CLIENT_SECRETle code secret du client

Google ne crée pas de compte tout seul : quelqu'un d'inconnu qui clique « Google » est renvoyé vers le formulaire de demande d'accès. Pour toi, mets ton adresse Gmail dans ADMIN_EMAIL et le bouton Google te reconnaîtra.

Phase 3 · réseau

Cloudflare : un tunnel pour tout le domaine

≈ 10 min

Un seul tunnel envoie super-nono.cc et tous ses sous-domaines vers Authentik. Rien n'est ouvert sur ta box.

Créer le tunnel « passerelle »

  1. Cloudflare Zero Trust → Réseaux → Tunnels → Créer un tunnel → Cloudflared, nom passerelle.
  2. À l'écran « Installer et exécuter un connecteur », choisis Docker et copie la longue valeur qui suit --token. N'exécute pas la commande : la passerelle s'en charge.
CLOUDFLARE_TUNNEL_TOKENla valeur après --token

Ajouter les deux routes

Étape suivante du tunnel, Noms d'hôte publics (ou Routes d'application publiées) :

1Sous-domaine vide, domaine super-nono.cc, service HTTP → server:9000
2Sous-domaine *, domaine super-nono.cc, service HTTP → server:9000

Si Cloudflare refuse parce qu'un enregistrement DNS existe déjà (souvent un A sur la racine), supprime cet enregistrement dans DNS puis recommence. Ne supprime pas encore les CNAME de tes sites actuels : ils continuent de marcher comme avant jusqu'à leur migration (phase 9).

Vérifier le DNS et Access

  • super-nono.cc → DNS : tu dois voir super-nono.cc et * en CNAME vers …cfargotunnel.com, nuage orange.
  • Aucun enregistrement ne doit exister pour auth : c'est le joker * qui l'attrape.
  • Zero Trust → Access → Applications : s'il y a une application sur super-nono.cc ou *.super-nono.cc, supprime-la, sinon tu aurais deux connexions à la suite.
Phase 4 · machine

Proxmox : créer le LXC « passerelle »

≈ 10 min

Créer le conteneur

Créer un CT, avec ces réglages :

Nompasserelle, non privilégié (case cochée)
ModèleDebian 13 (ou 12) standard
Disque16 Go
Processeur2 cœurs
Mémoire4096 Mo, swap 512 Mo
RéseauIP fixe, par exemple 192.168.1.40/24, passerelle de ta box. Note cette IP, elle sert au pare-feu des sites.

Autoriser Docker dans le conteneur

Avant de le démarrer : le CT → Options → Fonctionnalités → coche Imbrication (nesting) et keyctl. Coche aussi Options → Démarrer au boot. Puis démarre-le.

Phase 5 · installation

Installer la passerelle

≈ 15 min

Fais cette phase une fois la pull request fusionnée dans main. Tout se passe dans la console du LXC (Proxmox → le CT → Console), en root.

Récupérer le code

apt update && apt install -y git curl
git clone https://github.com/SuperNon0/site.git /opt/site
cd /opt/site/passerelle

Si le dépôt est privé, Git demande un identifiant et un mot de passe : mets ton pseudo GitHub et un jeton (GitHub → Settings → Developer settings → Personal access tokens → Fine-grained, accès en lecture seule au contenu du dépôt site).

Remplir le fichier .env

cp .env.example .env
nano .env

Remplis ces lignes avec les valeurs notées plus haut. Laisse la section « secrets » vide : le script la remplit tout seul.

ADMIN_EMAILton adresse (Gmail si tu veux le bouton Google)
CLOUDFLARE_TUNNEL_TOKENphase 3
GOOGLE_CLIENT_ID / _SECRETphase 2, ou vide
SMTP_USER / SMTP_PASSWORDphase 1
BOTPANEL_URLadresse locale de BotPanel, par exemple http://192.168.1.50:8080

Pour enregistrer dans nano : Ctrl + O, Entrée, puis Ctrl + X.

Lancer l'installation

./installer.sh

Le script installe Docker, génère les mots de passe internes, télécharge Authentik (quelques minutes), le démarre, puis le configure : page de connexion aux couleurs du hub, Google, invitations, compte de service du hub.

À la fin, un cadre affiche ton mot de passe provisoire. Note-le : il ne sera plus jamais affiché.

Le script peut être relancé sans risque : il ne refait que ce qui manque.

Phase 6 · premier essai

Première connexion

≈ 5 min

Entrer dans le hub

  1. Sur ton téléphone, ouvre super-nono.cc. La page de connexion apparaît (sur auth.super-nono.cc).
  2. Entre ton e-mail et le mot de passe provisoire. Tu arrives sur l'accueil du hub, vide pour l'instant.
  3. Réglages → Mon compte : change ton mot de passe.
  4. Réglages → Installer : ajoute le hub à l'écran d'accueil, il s'ouvrira comme une application.

Essayer Google et le mot de passe oublié

  • Déconnecte-toi (Réglages → Se déconnecter), puis reconnecte-toi avec Google.
  • Essaie Mot de passe oublié : l'e-mail doit arriver depuis acces@super-nono.cc. Regarde dans les spams la première fois.
Phase 7 · demandes d'accès

BotPanel : Accepter / Refuser depuis Discord

≈ 10 min

Quelqu'un remplit le formulaire sur super-nono.cc/demande, tu reçois un message Discord avec deux boutons. Il faut la version de BotPanel avec les boutons « webhook » (la mise à jour faite dans l'autre fil) : déploie-la d'abord.

Créer la notification hub_demande

BotPanel → Notifications → Nouvelle :

Slughub_demande
TitreNouvelle demande d'accès
Message**{var:nom_complet}** ({var:email}) demande un accès à {var:site}.
> {var:message}

Variables disponibles : id, prenom, nom, nom_complet, email, message, lien, site.

Ajouter les trois boutons

Acceptervert, type webhook, adresse ci-dessous, données {"action": "accepter", "id": "{var:id}"}
Refuserrouge, type webhook, même adresse, données {"action": "refuser", "id": "{var:id}"}
Ouvrir le hubgris, type lien, adresse {var:lien}
https://super-nono.cc/api/botpanel/decision

Le hub répond dans Discord, par exemple « Accès accordé à Léa : l'invitation est partie par e-mail ».

Partager le secret de signature

  1. BotPanel → Paramètres → Intégrations → copie le secret webhook.
  2. Dans la console de la passerelle :
cd /opt/site/passerelle
nano .env            # BOTPANEL_WEBHOOK_SECRET=le secret
docker compose up -d

Sans ce secret, le hub refuse les clics (« Signature BotPanel invalide »). C'est ce qui empêche n'importe qui d'accepter une demande à ta place.

Faire un essai complet

  1. Dans une fenêtre de navigation privée, ouvre super-nono.cc/demande et fais une demande avec une autre adresse à toi.
  2. Le message arrive sur Discord, et la personne reçoit un accusé de réception avec un lien de suivi.
  3. Clique Accepter : un e-mail d'invitation part. Le lien ouvre une page où l'on choisit son mot de passe ; le compte est créé dans le groupe « Membres » et la personne arrive sur le hub.
  4. Tu peux aussi tout faire depuis le hub : Demandes (accepter, refuser, renvoyer l'invitation, effacer).
Phase 8 · tes sites

Ajouter les sites et fermer les portes

≈ 5 min par site

Ajouter un site dans le hub

Hub → Sites → Ajouter :

Nomce qui s'affiche sur le bouton
Sous-domainerecettes pour recettes.super-nono.cc
Adressel'IP et le port du LXC, par exemple 192.168.1.60:3000 (bouton Tester pour vérifier)
Accès« Membres » ou « Admins seulement »
Chemins publics/api/notify, /mcp, /.well-known et /oauth par défaut : joignables sans passer par la page de connexion (les deux derniers servent à Claude pour se connecter au MCP avec ton compte)

Le hub crée tout seul la protection dans Authentik. Un site peut aussi être un simple lien externe.

Pare-feu Proxmox : seule la passerelle entre

Une seule fois, avant tout : Centre de données → Pare-feu → ajoute deux règles « Entrée, ACCEPT » depuis ton réseau (source 192.168.1.0/24), ports 8006 et 22. Ensuite seulement Options → Pare-feu : Oui. Sinon tu risques de perdre l'accès à Proxmox.

Puis pour chaque LXC de site :

  1. Le CT → Pare-feu → Ajouter : Entrée, ACCEPT, source 192.168.1.40 (IP de la passerelle), port de destination = port du site.
  2. Ajoute aussi SSH depuis ton réseau, et les machines qui appellent le site en direct sur son adresse locale. BotPanel en premier : tous tes sites lui envoient leurs notifications, donc autorise leurs IP (ou tout ton réseau) sur son port. Le hub explique tout ça dans Plus → Brancher un projet.
  3. Pare-feu → Options : Pare-feu Oui, politique d'entrée DROP.
  4. Vérifie : le site marche par https://…super-nono.cc, mais plus en tapant son IP depuis ton PC.
Phase 9 · ménage

Retirer l'ancien Cloudflare Access, site par site

≈ 10 min par site

Fais un site à la fois, dans cet ordre, et passe au suivant seulement quand le premier marche.

Basculer le site sur la passerelle

  1. Ajoute le site dans le hub (phase 8), avec le même sous-domaine qu'aujourd'hui.
  2. Cloudflare → DNS : supprime le CNAME propre à ce site. Le joker * prend le relais et l'envoie à la passerelle.
  3. Zero Trust → Access → Applications : supprime l'application de ce site.
  4. Ouvre le site : la connexion de la passerelle apparaît, puis le site.

Faire lire la nouvelle identité au site

Les sites qui lisaient le jeton Cloudflare (BotPanel avec cloudflare_access.py, RecipeLogs avec cloudflare.ts) doivent maintenant lire l'en-tête X-Authentik-Email, et seulement si l'en-tête X-Passerelle-Cle vaut le secret PASSERELLE_CLE du .env de la passerelle. Le code prêt à copier (Python et TypeScript) est dans passerelle/docs/migrer-un-site.md. Pour l'afficher :

grep PASSERELLE_CLE /opt/site/passerelle/.env

Tant que le site n'est pas modifié, il peut te redemander de te connecter « à l'ancienne ». Demande-moi la modification dans le fil du site concerné.

Supprimer l'ancien tunnel du site

  1. Si le site avait son propre tunnel : Zero Trust → Réseaux → Tunnels → supprime ses routes, puis le tunnel.
  2. Dans le LXC du site :
systemctl disable --now cloudflared
apt remove -y cloudflared

Ne touche jamais au tunnel passerelle.

Ensuite

Au quotidien

Mettre à jour (et après chaque changement du .env)

cd /opt/site/passerelle && ./mettre-a-jour.sh

Sauvegarde la base d'Authentik (les 7 dernières dans data/sauvegardes/), récupère le nouveau code, redémarre et reconfigure. Le numéro de version est visible dans Réglages.

Programmer une sauvegarde du LXC

Proxmox → Centre de données → Sauvegarde → Ajouter : le CT passerelle, chaque semaine, mode instantané. Tout ce qui compte est dans /opt/site/passerelle/data et .env.

Garder la commande de secours

Si tu ne peux plus entrer du tout, ce lien de connexion valable une heure t'ouvre l'administration d'Authentik. Ajoute https://auth.super-nono.cc devant le chemin affiché.

cd /opt/site/passerelle && docker compose exec worker ak create_recovery_key 60 akadmin

Si quelque chose ne marche pas

Erreur Cloudflare 502 ou 1033La passerelle est arrêtée ou la route du tunnel est fausse : elle doit être HTTP → server:9000. Regarde docker compose ps.
Google affiche « redirect_uri_mismatch »L'URI de redirection chez Google doit être exactement https://auth.super-nono.cc/source/oauth/callback/google/, avec le / final.
Les e-mails n'arrivent pasVérifie SMTP_USER, SMTP_PASSWORD et que le domaine est « Authentifié » dans Brevo, puis lance ./mettre-a-jour.sh. Quand l'envoi échoue, le hub te donne le lien d'invitation à transmettre toi-même.
Discord répond « Signature BotPanel invalide »Le secret webhook de BotPanel et BOTPANEL_WEBHOOK_SECRET ne sont pas identiques, ou l'heure d'une des machines est fausse de plus de 5 minutes.
Pas de message Discord à une demandeBOTPANEL_URL doit être joignable depuis la passerelle, et la notification doit s'appeler exactement hub_demande.
Voir ce qui se passedocker compose logs -f --tail 50 server hub
